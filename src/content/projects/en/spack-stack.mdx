## The situation

HBKU's research computing environments spanned four HPC platforms with
different schedulers, operating systems, and hardware generations: a Cray
XC40, an NVIDIA Volta-era GPU cluster, a Cray XC50, and an AWS ParallelCluster
cloud cluster. Researchers and administrators needed a maintainable way to
build and provide scientific software across that varied estate, while making
clear which software was centrally supported and where researchers could
manage their own environments.

## Constraints

- The software stack had to accommodate platform-specific differences across four production systems.
- Administrators needed a curated, production-validated application layer without making every researcher depend on individually managed installs.
- Researchers needed room to build their own environments on top of shared dependencies, without duplicating the foundation stack.
- Support expectations needed to be explicit for system-wide, community-managed, and user-managed software.

## Approach

I designed and deployed a three-layer software stack with Spack. The
Foundation layer contains administrator-managed compilers, MPI
implementations, and core libraries. The Application layer provides research
applications selected and validated by administrators. Researchers can use
the User layer to build environments on top of the shared foundation.

The catalog includes the Intel oneAPI toolchain, Python, PyTorch,
TensorFlow, GROMACS, LAMMPS, CP2K, GATE, and core libraries such as FFTW,
OpenBLAS, HDF5, and NetCDF. I resolved compatibility issues specific to each
platform, including the Cray XC40. I also created environments for
geospatial processing with PDAL, GDAL, and rasterio, and for molecular
dynamics with GROMACS, Intel MPI, and OpenMP.

## Key decisions

I separated software into layers with distinct ownership. Administrators
manage core build dependencies in Foundation and curate the production
applications in Application. Researchers can build their own environments in
User while reusing the shared foundation.

Spack is the common platform for building and managing software across all
four systems. Platform-specific compatibility requirements are handled on
each system.

I wrote RCCG's software governance policy to define support for
system-wide, community-managed, and user-managed software. It also sets
standards for reproducible use of GPU and network resources, including
containerized workflows.

## Outcome

The three-layer Spack architecture is in production across four HPC platforms.
It supports the scientific software catalog and research-specific
environments, and provided the basis for RCCG's software governance policy.
